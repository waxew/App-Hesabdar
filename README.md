# حسابدار (App-Hesabdar)

نرم‌افزار حسابداری تخصصی اندروید با رویکرد Offline-First و دیتابیس کاملاً محلی. هدف پروژه ساخت یک هسته حسابداری مستقل و قابل‌گسترش در کلاس نرم‌افزارهای حسابداری عمومی مانند هلو و پارمیس است؛ بدون کپی کد یا رابط کاربری آن‌ها.

## وضعیت فعلی

- نسخه توسعه: `0.2.0`
- `versionCode = 2`
- `applicationId = com.waxew.hesabdar`
- Kotlin + Jetpack Compose + Material 3
- Room + SQLite برای ذخیره‌سازی محلی
- `minSdk = 24`
- `targetSdk = 35`
- رابط فارسی و راست‌به‌چپ

نسخه 0.2.0 اولین هسته عملیاتی حسابدار است و علاوه بر اشخاص و کالاها، خرید، فروش، تسویه اولیه، گردش موجودی و داشبورد مالی واقعی را شامل می‌شود.

## امکانات فعال

- داشبورد مالی با جمع فروش، خرید، مطالبات و بدهی‌ها
- اشخاص و طرف‌حساب‌ها
- کالاها با قیمت خرید، قیمت فروش و موجودی
- ثبت فروش
- ثبت خرید
- ثبت مبلغ دریافت‌شده یا پرداخت‌شده هنگام فاکتور
- محاسبه مانده فاکتور
- کاهش خودکار موجودی در فروش
- افزایش خودکار موجودی در خرید
- کارتکس فنی انبار در دیتابیس
- ثبت فاکتور و ردیف‌های فاکتور در Room
- ثبت عملیات چندمرحله‌ای داخل Transaction
- Migration دیتابیس 1 به 2 بدون حذف اطلاعات قبلی

## اصول ثابت پروژه

1. اطلاعات اصلی کاربر داخل گوشی ذخیره می‌شود و برای کارکرد پایه اینترنت لازم نیست.
2. مبالغ مالی با `Long` ذخیره می‌شوند؛ برای پول از `Float` و `Double` استفاده نمی‌شود.
3. هر تغییر Schema باید Migration مشخص داشته باشد.
4. در نسخه Production از `fallbackToDestructiveMigration` استفاده نمی‌شود.
5. نسخه جدید باید روی نسخه قبلی نصب شود و اطلاعات کاربر حفظ شود.
6. عملیات مالی چندمرحله‌ای Atomic و Transactional هستند.
7. UI اجازه تغییر مستقیم همزمان چند جدول مالی را ندارد؛ عملیات از لایه مرکزی AccountingRepository عبور می‌کند.
8. کدهای مهم پروژه با توضیح و کامنت نگهداری می‌شوند.

## Build و APK

GitHub Actions روی Push به شاخه `main` دستور زیر را اجرا می‌کند:

```bash
gradle :app:assembleDebug --stacktrace
```

APK دیباگ به‌عنوان Artifact با نام نسخه ذخیره می‌شود.

## سیاست انتشار و آپدیت

- `applicationId` ثابت می‌ماند.
- `versionCode` در هر انتشار افزایش می‌یابد.
- Release نهایی با Keystore ثابت امضا می‌شود.
- فایل Keystore خصوصی داخل Repository عمومی Commit نمی‌شود.
- هر تغییر Room Schema دارای Migration صریح خواهد بود.
- قبل از انتشار نسخه‌های پایدار، Upgrade از نسخه قبلی و حفظ داده تست می‌شود.
